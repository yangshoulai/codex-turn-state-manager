# Codex Turn-State Manager 插件 — 需求、功能设计、技术架构与开发计划文档

**文档版本**：v1.1

**目标插件名称**：`codex-turn-state-manager`

**目标平台**：CLIProxyAPI (CPA)

**文档状态**：开发前设计基线


## 一、项目概述

### 1.1 背景

CPA 中的 Codex 账号在调用上游 Responses API 时，响应头中会携带 `X-Codex-Turn-State` 字段。该字段在 Codex 官方源码中被定义为 per-turn sticky-routing token，用于同一 turn 内的路由粘滞。官方文档明确其使用方式为：服务器在 turn 开始时返回该 token，客户端在同一 turn 内的后续请求中回放该 token，**不跨 turn 使用**。

但实际观测表明，长度恰好为 292 的 turn-state 值可能在**账号 + 模型**维度上跨 turn 复用，从而实现更优的上游路由稳定性。

本插件通过**定时探测 + 请求头替换 + 响应头反向捕获**的机制，实现 `(authIndex, model)` 级别的 Turn-State 绑定与复用，并在 CPA 的账号调度策略中优先选择已绑定有效 State 的账号。

### 1.2 核心目标

1. 对 CPA 中已配置的 Codex 账号，按账号 + 模型维度进行定时探测，获取目标长度（默认 292）的 `X-Codex-Turn-State` 值。
2. 拦截 CPA 对外请求，在已绑定有效 State 时自动替换 `X-Codex-Turn-State` 请求头。
3. 从正常业务流量的响应头中反向捕获 State，实现“被动续期”，降低主动探测频率。
4. 干预 CPA 的账号选择策略，优先使用已绑定有效 State 的 `(账号, 模型)` 组合。
5. 提供一个全局总开关；总开关关闭时，探测、响应拦截、请求拦截、账号选择干预四项运行能力全部旁路。
5. 提供独立的管理面板，展示账号、模型、State 绑定状态、代理池健康状况及探测历史。

### 1.3 协议风险声明

Codex 官方将 `x-codex-turn-state` 定义为 **per-turn sticky-routing token**，同一 turn 内复用，不应跨 turn 使用。本插件的“账号+模型级 TTL 缓存”属于**基于实际观测的实验性策略**，架构上必须设计为可关闭、可快速 invalidate、有自动 fallback 的模式。一旦检测到由注入 State 引起的请求失败（如 `previous_response_not_found`、连续 5xx 等），插件应立即失效对应绑定并后台重新探测。

## 三、功能设计

### 3.1 模块划分

```
Codex Turn-State Manager Plugin
├── AccountRegistry          — CPA 账号同步与状态追踪
├── ModelRegistry            — 模型能力表（reasoning 最低级别等）
├── StateRegistry            — State 绑定管理 + 内存快照 + 历史记录
├── ProbeScheduler           — 定时扫描 + 探测队列调度 + 时间窗口判断
├── TimeWindowManager        — 探测时间窗口配置与判定
├── ProbeExecutor            — 代理遍历 + 凭证获取 + HTTP 探测
├── ProxyPool                — 代理节点健康管理 + 冷却排序
├── RequestStateInjector     — 请求拦截 + State 注入
├── ResponseStateCollector   — 响应头捕获 + 被动绑定
├── CredentialScheduler      — 干预 CPA 账号选择策略
├── CorrelationManager       — RequestID/AuthID 关联映射
├── PersistenceManager       — SQLite 持久化 + 启动恢复 + Schema 迁移
├── ManagementAPI            — 管理接口
└── ResourceUI               — 管理面板前端
```

### 3.2 状态模型

每个 `(authIndex, model)` 对的 State 绑定具有以下状态：

```
FRESH          — 剩余有效期 > 15%，正常使用
REFRESH_DUE    — 仍有效但剩余 <= 15%，后台应触发重新探测
MISSING        — 无绑定 State
EXPIRED        — 绑定 State 已过期
```

TTL 计算规则：

```
bound_at      = 绑定时刻
expires_at    = bound_at + TTL（默认 60 分钟）
refresh_after = bound_at + TTL × 85%（默认 51 分钟）
```

**绑定历史记录**：每次 State 绑定变更（新增、替换、手动删除）均记录到 `state_binding_history` 表，供面板按模型维度展示。历史记录包含 State 值、来源（probe/traffic/manual）、绑定时间、有效期、操作类型。

### 3.3 全局开关设计

插件提供一个总开关和两个子开关。管理面板、Management API、状态查询和历史记录在总开关关闭时仍可用；总开关只控制运行时行为。总开关默认 **ON**，用于保持首次升级前的行为兼容。

| 开关 | 默认值 | 作用 |
|------|--------|------|
| **全局总开关** | ON | 统一控制探测、响应拦截、请求拦截、账号选择干预、调用历史记录。OFF 时五项功能全部旁路，已绑定 State 也不得注入或刷新 |
| **定时探测开关** | ON | 仅在总开关 ON 时控制 ProbeScheduler 的主动探测 |
| **反向绑定开关** | ON | 仅在总开关 ON 时控制 ResponseStateCollector 从正常业务响应头捕获并绑定 State |
| **状态优先开关** | ON | 仅在总开关 ON 时控制 CredentialScheduler 是否干预账号选择。关闭后调度永远 DelegateBuiltin，但 State 注入不受影响 |

运行时判定规则：

```
if !global_enabled:
    ProbeScheduler          → 不入队、不发起主动探测
    RequestStateInjector    → 不修改请求头，不注入 State，不写 correlation
    ResponseStateCollector  → 直接忽略响应头，不捕获、不刷新、不替换绑定
    CredentialScheduler     → DelegateBuiltin，不干预账号选择
    CallRecorder            → 不记录任何调用历史
else:
    ProbeScheduler          → 再检查 global_probe_enabled 和时间窗口
    RequestStateInjector    → 按账号+模型查询有效 State 并决定是否注入
    ResponseStateCollector  → 再检查 global_reverse_bind_enabled
    CredentialScheduler     → 再检查 state_priority_enabled，关闭则 DelegateBuiltin
```

三个子开关只在总开关开启时生效，互不影响。

**调用历史只由总开关把守，不受三个子开关影响。** 它记录的是「插件对这个请求做了什么」，而这正是运维关掉某个能力时最想问的问题——把它挂在反向绑定子开关下面，会让「关掉捕获」同时关掉看清楚发生了什么的能力。总开关关闭时插件不记录任何东西，这是刻意的：关掉的插件应该看起来像从未加载过，而不是像在悄悄观察。

**账号同步不受探测开关与时间窗口限制。** 它是读一次 CPA 的账号列表，不是探测。放在闸门之后曾经导致窗口之外账号状态冻结（见 10.11）。

**为什么调度干预要单独一个开关**：改写请求头只影响这一个请求，而干预账号选择是在覆盖 CPA 自身的负载均衡。这两件事的侵入性不同，所以不共用一个开关。状态优先开关关闭时，插件仍然注入已持有的 State，只是不再影响选中哪个账号。

- **总开 + 探测开 + 反向绑定开**（默认）：主动探测 + 被动捕获双通道
- **总开 + 探测开 + 反向绑定关**：仅主动探测，禁止业务响应捕获
- **总开 + 探测关 + 反向绑定开**：仅依赖正常业务流量被动积累 State
- **总开 + 探测关 + 反向绑定关**：停止 State 获取，但仍允许已有有效 State 注入和账号选择干预
- **总开关关**：四项运行能力全部停止；已有绑定保留在数据库中，重新打开后可继续使用，过期绑定仍按 TTL 判定

切换总开关为 OFF 时，应取消或标记当前排队及运行中的主动探测；无法立即中断的 HTTP 请求在返回后丢弃结果，不得写入绑定。全局开关状态持久化到 SQLite `settings` 表，CPA 重启后自动恢复。

### 3.4 定时探测时间窗口

定时探测支持配置多个时间窗口，探测任务启动前判断当前时间是否落在任一配置窗口内，仅窗口内执行实际探测。

**配置格式**：

```
TimeWindow {
  id:          string,
  label:       string,    // 如 "工作时段"
  daysOfWeek:  []int,     // 0=周日 ... 6=周六，空表示每天
  startTime:   string,    // "08:00"
  endTime:     string,    // "20:00"
  enabled:     bool,
}
```

**判定逻辑**：

```
func shouldProbeNow():
    windows = getEnabledWindows()
    if len(windows) == 0:
        return true         // 未配置窗口时，默认全天可探测
    now = currentTime()
    for w in windows:
        if !w.enabled:
            continue
        dayMatched = len(w.daysOfWeek) == 0 || now.dayOfWeek in w.daysOfWeek
        if !dayMatched:
            # 跨天窗口的次日凌晨部分属于前一天窗口
            if w.startTime > w.endTime && now.time <= w.endTime:
                dayMatched = previousDay(now.dayOfWeek) in w.daysOfWeek || len(w.daysOfWeek) == 0
        if !dayMatched:
            continue
        if w.startTime <= w.endTime and w.startTime <= now.time <= w.endTime:
            return true
        if w.startTime > w.endTime and (now.time >= w.startTime or now.time <= w.endTime):
            return true
    return false
```

**多窗口支持**：可配置多个窗口，如 `08:00–12:00` 和 `14:00–20:00`。窗口可跨天（如 `22:00–06:00`）。时间窗口配置持久化到 SQLite，CPA 重启后自动恢复。

### 3.5 探测调度算法

扫描间隔默认 1 分钟，但**扫描不等于探测**。50 个 `(账号, 模型)` 对在 TTL=60min、15% 提前更新下的稳态探测频率约为 0.98 probe/min。

探测并发数 `maxProbeConcurrency` 默认 **2**，可配置。该值控制 ProbeExecutor 同时执行的探测任务数量，即同时占用槽位的 `(账号, 模型)` 探测数。每个探测任务内部遍历所有可用代理节点时，是在该槽位内串行进行的，不会为每个代理额外开并发。

```
Scanner 每分钟执行：
  1. 到了账号同步间隔（默认 5 分钟）→ 同步 CPA 最新 Codex 账号列表
     —— 这一步在所有闸门之前：它只是读一次账号列表，不是探测。
        放在闸门之后会让窗口之外的账号状态冻结（见 10.11）
  2. 检查全局总开关 → 关闭则返回
  3. 检查全局定时探测开关 → 关闭则返回
  4. 检查当前时间是否在探测窗口内 → 不在窗口内则返回
  5. 对本轮涉及的每个账号调用一次 SyncAccount（实时状态，见 10.11）
     —— 按账号一次，不按 pair 一次：同一账号下的多个模型问的是同一个问题
  6. 遍历每个启用的 (account, model)：
     a. pair 探测开关关闭 → skip
     b. 已有探测进行中 → skip
     c. now < next_probe_at → skip
     d. State 状态为 FRESH → skip
     e. 入队探测
  7. 探测队列受 maxProbeConcurrency（默认 2）限制
```

首次安装时所有 pair 无 State，需通过 jitter 摊开，避免瞬时 50 个并发请求。

### 3.6 探测请求设计

探测直接访问 Codex 上游，不走 CPA 正常 `/v1/responses` 路径。原因：CPA Host HTTP API 不支持 per-request proxy 参数。

**请求构造**：

```
POST /backend-api/codex/responses
Headers:
  Authorization: Bearer <从 host.auth.get 实时获取的 access_token>
  Content-Type: application/json
Body:
{
  "model": "<目标模型>",
  "stream": true,
  "store": false,
  "tools": [],
  "input": [{"role": "user", "content": [{"type": "input_text", "text": "."}]}],
  "reasoning": { "effort": "<模型最低支持的级别>" }
}
```

**不要加 `max_output_tokens`——这个端点不接受它。** 这里记一次踩过的坑，因为"给探测加输出上限"看起来是最显然的省钱办法：

| 证据 | 结论 |
|---|---|
| Codex CLI 的 `ResponsesApiRequest`（`codex-rs/codex-api/src/common.rs`） | **没有这个字段**。不是条件序列化，是结构体里不存在 |
| CPA 的 Codex 执行器 | 构造请求体只 set `instructions` / `tools`，从不发送它；相关命中全在**解析**响应的 `incomplete_details.reason` |
| 上游模型目录 `codex_client_models.json` | 没有任何 min/max output token 字段 |
| 实测 | 同一个账号同一个模型，加上该字段后上游返回 **400**，无 state 头 → 归类为 `UPSTREAM_ERROR`，该 pair 静默不再绑定 |

陷阱在于**公开的 OpenAI Responses API 确实文档化了这个参数**，而这个端点是 Codex CLI 的私有端点。把一个语境里的事实搬到另一个语境，是这份文档已经犯过两次的错误。

**这个端点支持的省 token 手段已经都在最低档了**：模型能接受的最低 reasoning effort（`models.Registry` 提供），以及 verbosity——模型目录里每个模型都是 `support_verbosity: true` 且 `default_verbosity: low`，也就是默认已经是最低值。所以**探测的单次成本无法靠请求形状再压**，能压的只有探测次数，那是调度器的退避与遍历上限的职责。

**模型能力表**：不同模型最低 reasoning 级别不同（`none` / `minimal` / `low`），插件应维护 `ModelCapability` 映射而非硬编码。

**响应处理**：收到 HTTP response headers 后立即检查 `X-Codex-Turn-State`，命中目标长度则原子更新绑定，然后立即关闭 body，不等待 SSE 完成。Codex 源码确认在收到 response headers 后即读取该字段。

**429 是账号级事实，不遍历代理池。** 之前 429 会继续走下一个节点。真正会碰到的限流是那个多小时的使用窗口，而它是**账号**的属性：下一个节点问的是同一个上游、同一个账号，得到的还是 429——于是一轮探测用 N 个计费请求换来 N 个同样的拒绝。现在 `OutcomeRateLimit` 与 `AUTH_ERROR` / `MODEL_UNSUPPORTED` 一样属于 `Terminal()`，立即结束本轮，并且**不冷却节点**（限流不是代理的错）。

> 与上面那条封顶不同，这一条不依赖"节点是否影响结果"的假设：无论节点有没有影响，账号级限流的回答都不变。

### 3.7 代理池设计与探测遍历策略

#### 3.7.1 代理节点状态

每个代理节点维护运行状态：

```
ProxyNode {
  id, url, enabled,
  successCount, failureCount,
  lastUsedAt,               // 最近一次被使用的时间（无论成功失败）
  lastSuccess, lastFailure,
  consecutiveFailures,
  cooldownUntil,
  latency
}
```

`lastUsedAt` 在每次探测使用该节点后立即更新并持久化到 `proxy_node` 表，用于实现“优先选择冷却最久的代理”策略。

#### 3.7.2 代理节点选择顺序

从代理池选取节点时，按以下优先级排序：

```
1. 过滤 enabled = true 且 cooldownUntil <= now 的节点
2. 按 lastUsedAt 升序排列（即最久未被使用的优先）
3. lastUsedAt 为 NULL 的节点视为最早使用，排在最前
4. 若 lastUsedAt 相同，按 id 升序保证稳定顺序
```

该策略确保代理流量均匀分布，避免某个节点被频繁使用。

#### 3.7.3 单次 `(账号, 模型)` 探测的代理遍历逻辑

每次对某个 `(账号, 模型)` 发起探测时，遍历可用代理节点，直到获得目标 State 值、本轮不可用次数达到上限、或节点走完：

> **遍历的默认上界仍然是"走完可用节点"，`max_unusable_per_probe` 默认 0 即不封顶。**
>
> 该封顶建立在一条**尚未验证的假设**上：认为多个节点会给出同一个"不可用"答案，所以走完剩下的节点只是把同一个答案按节点数再买一遍。支持它的是信封的结构——块数从值自身的信封读出，信封只有版本号、签发时间和密文，**没有任何字段能编码请求的出口 IP**，目前唯一观察到与块数相关的是账号套餐。反对它的是：上游仍可能因为出口 IP 信誉**选择**不同的回复，"信封不携带 IP"不等于"IP 影响不了答案"。
>
> 原始设计假定的是相反方向（非目标长度让该节点对当前 pair 进冷却，换一个节点再试），运维自己的观察也指向那一侧。所以默认不动，需要时由运维自行调小——这是一个成本与"找到可用节点的机会"之间的取舍，应当由拿到数据的人来做，而不是基于未实测的推断替他做。
>
> **怎么用现有数据判定**：`probe_history` 按 (pair, proxy) 记了 `state_length`。同一个 pair 在相近时间经不同节点返回**相同**长度 → 支持该假设；返回**不同**长度 → 推翻它。
>
> 代理**故障**（NETWORK_ERROR）不受此限，那是节点自身的问题，值得换一个。

```
func probeWithAllProxies(authIndex, model):
    proxies = proxyPool.getAvailableOrderedByCooldown()  // 已按 lastUsedAt 升序
    if len(proxies) == 0:
        return PROBE_NO_PROXY_AVAILABLE

    deadline = now + maxProbeDuration   // 默认 90 秒
    lastResult = nil

    for proxy in proxies:
        if now > deadline:
            return PROBE_TIMEOUT_ALL_PROXIES

        // 标记使用时间（立即持久化）
        proxy.lastUsedAt = now
        persistProxyNode(proxy)

        // 实时获取 access_token（不缓存）
        credential = host.auth.get(authIndex)
        accessToken = credential.access_token

        result = sendProbeRequest(proxy, accessToken, model)

        // 记录探测历史（含代理 id、结果、耗时）
        recordProbeHistory(authIndex, model, proxy.id, result)

        if result.type == SUCCESS_TARGET:
            // 命中目标 State，立即绑定并返回
            bindState(authIndex, model, result.state, source='probe', proxyId=proxy.id)
            return result

        if result.type == SUCCESS_NON_TARGET:
            lastResult = result
            continue

        if result.type == AUTH_ERROR or result.type == MODEL_UNSUPPORTED:
            // 账号或模型级问题，换代理也无法解决，直接终止遍历
            return result

        if result.type == RATE_LIMIT:
            // 账号级限流：换出口 IP 面对的是同一个上游、同一个账号。
            // 像 AUTH_ERROR 一样终止本轮，且不冷却节点。
            return result
            continue

        if result.type == NETWORK_ERROR:
            // 代理故障，标记冷却后继续下一个
            markProxyCooldown(proxy, backoffFor(proxy.consecutiveFailures))
            lastResult = result
            continue

    return lastResult  // 所有代理均尝试完毕，返回最后一次结果
```

**关键规则**：

1. **目标优先**：只要某个代理返回了长度等于目标值的 State，立即绑定并终止遍历。
2. **账号/模型级错误直接终止**：`AUTH_ERROR`、`MODEL_UNSUPPORTED` 与代理无关，换代理无意义，直接返回。
3. **代理故障标记冷却**：`NETWORK_ERROR`（timeout、connect error、TLS error、407）才触发代理冷却；OpenAI 返回的 400/401/403/429 **不**踢掉代理节点。
4. **`lastUsedAt` 实时更新**：每次使用前即写入，确保并发探测时其他 worker 能看到最新使用时间，避免同时选中同一节点。
5. **总时长上限**：单次 `(账号, 模型)` 探测遍历所有代理的总时长受 `maxProbeDuration`（默认 90 秒）限制，超时立即终止并记录 `PROBE_TIMEOUT_ALL_PROXIES`。
6. **并发控制**：遍历过程占用一个 `maxProbeConcurrency`（默认 **2**）槽位，避免过多账号模型同时遍历大量代理。

#### 3.7.4 代理故障判定规则

- **是代理故障**：timeout、connect error、TLS error、407 → 标记冷却，继续下一个代理
- **不是代理故障**：OpenAI 返回的 400 / 401 / 403 / 429 → 不踢掉代理节点，但根据错误类型决定是否继续遍历

### 3.8 请求拦截与 State 注入

**本节已按 CPA v7.3.7 的实际接口重写。** 原设计假设 AfterAuth 阶段拿不到 AuthID，因此用「BeforeAuth 注入临时 correlation header → Scheduler 读取 → AfterAuth 读回」的方式关联账号身份。核对 CPA 源码后确认：

- `RequestInterceptRequest` 确实没有任何 auth 字段；
- 但 conductor 在调用 after-auth 钩子**之前**，会把 `selected_auth_id` 与 `selected_auth_index` 写入 `Metadata`（`sdk/cliproxy/auth/conductor_execution.go`）。

因此 correlation header 机制**已整体移除**：不注入、不清理、不存在泄漏到上游的风险，也少了一个拦截阶段。插件只实现 `request.intercept_after` 一个阶段。

```
AfterAuth 阶段（request.intercept_after）：
  从 Metadata 读 selected_auth_id / selected_auth_index
  若总开关关闭 → 不改请求头
  若 auth_index 为空 → 不注入（Metadata 是 best-effort，缺失只降级不报错）
  查询 StateRegistry(auth_index, model)
  若有效 → 返回 Headers: {X-Codex-Turn-State: <绑定的State值>}
```

只回传插件自己写入的那一个 header：把整个 header map 回传等于把请求原样反射给 host。

`Metadata` 在 CPA 中被描述为 "best-effort cloned context snapshot"，那两个 key 属于内部约定而非对外契约。因此缺失 key 必须降级为「账号未知、不注入」，绝不能导致请求失败。

**CorrelationManager 保留但职责收窄**：不再承担 header 传递，只记录「这个 request id 用了哪个 pair、是否真的注入过」，供响应阶段与自愈规则使用。自愈的前置条件依赖 `Injected` 这个标志，而不是靠推断。

### 3.9 响应头反向绑定

当**全局总开关和反向绑定开关均为 ON** 时，CPA 的 `StreamChunkInterceptor` 在 `StreamChunkHeaderInitIndex = -1` 回调中，**把响应携带的 State 与本次请求实际注入的值做比对**，据此决定是否要修正绑定：

| 响应值与请求时的值 | 处理 |
|---|---|
| 相同 | 绑定仍然有效，**不改动绑定值**；仅延长 TTL，不写历史 |
| 不同，且长度等于目标值 | 直接采纳为新绑定（`source=traffic`），写历史 |
| 不同，且长度不等于目标值 | **丢弃现有绑定及其有效期**，并清除该 pair 的探测退避，让下一轮扫描立即重探 |
| 响应中没有该头 | 不处理 |
| 无绑定可丢（第三种情况但本就没绑定） | 不处理，也不清除退避 |

**第三种情况是这个机制的价值所在**：上游返回了一个与所持值不同的、不可用的 token，说明手上的绑定描述的是上游已经不再签发的值。若继续用它，插件会在整个 TTL 内持续注入一个过期的 token，而本该修复它的探测任务还在等一个**问题发生之前就排好的退避**。丢弃 + 清除退避让自愈在一轮扫描内完成。

**第五种情况同样重要**：没有绑定可丢时若也清除退避，会把 `MODEL_UNSUPPORTED` 的 30 分钟冷却等主动退避一并抹掉，等于让每个响应都成为重探的理由。因此只在**确实丢弃了绑定之后**才清除退避。

原逻辑：

```
读取 RequestID
→ 查 executionMap 得到 authID
→ 读取 Model
→ 检查 X-Codex-Turn-State
→ 若长度 == 目标值：
    - 若已绑定相同值 → 刷新 TTL
    - 若值不同 → 原子替换 + 刷新 TTL + 记录历史
→ 清理 executionMap[RequestID]
```

正常业务流量本身即可为 State 续命，进一步降低主动探测频率。

### 3.10 探测失败退避策略

```
SUCCESS_TARGET            → next_probe_at = now + TTL × 85%
SUCCESS_NON_TARGET        → next_probe_at = now + 2~5 分钟
PROBE_NO_PROXY_AVAILABLE  → next_probe_at = now + 5 分钟
PROBE_TIMEOUT_ALL_PROXIES → next_probe_at = now + 5 分钟
NETWORK_ERROR             → 单代理退避 1m→2m→4m→8m→16m→32m→64m（封顶后计数归零）；整体 next_probe_at = now + 2 分钟
SUCCESS_NON_TARGET        → 同样让该节点进入上述冷却：请求成功但没给出目标长度，说明这个节点对当前 pair 没有产出，下一轮换一个
RATE_LIMIT (429)          → 有 Retry-After 头就按它；没有则 now + 10 分钟（原为 5 分钟）
AUTH_ERROR (401)          → 等待 CPA auth refresh，30 分钟后重试
MODEL_UNSUPPORTED         → 30 分钟后重试或自动禁用
```

“每分钟扫描”和“每分钟探测”是两个完全不同的概念，绝不能因为非目标长度 State 而每分钟重复探测。

**`Retry-After` 曾经是一个接线缺口。** `Backoff` 一直有 `RetryAfter` 字段并会使用它，但**没有任何地方填充过**——executor 从未读取该响应头，scheduler 也从未传递它。于是一次 429 永远落在 `DefaultRetryAfter` 上，而上游明明给出了自己想要的等待时长。现在 `Executor.parseRetryAfter` 解析两种 HTTP 写法（秒数与 HTTP-date），经 `Result.RetryAfter` 交给 `Backoff`；缺失或解析失败退回默认值，绝不因此报错。

默认值同时从 5 分钟提到 **10 分钟**：能收到无头 429 的场合，就是多小时使用窗口在拒绝这个账号，几分钟后重试只是再买一个 429。

**额度耗尽：这是唯一一个"晚点再来"里值得停止探测的。** 一次超额探测仍然返回 200 并带上响应头，所以**探测结果本身永远不会告诉你账号已经没额度了**——这正是它曾经烧掉运维整个 5h 窗口的原因。两个免费来源会说出这件事，`accounts.Judge` 都读：

| 来源 | 判据 | 恢复时间 |
|---|---|---|
| CPA 账号列表 | `next_retry_after` 未到 **且** `status_message` 命中额度关键词 | `next_retry_after` |
| 正常业务流量 | `X-Codex-Primary/Secondary-Used-Percent` 达到 100%（`Signals.ExhaustedUntil`） | 两个窗口 reset 里较晚的那个 |

**没有写明恢复时间的冷却不在此列**，仍然照常探测——那时没有比探测更好的估计。`ExhaustedUntil` 同样只认*未来*的 reset：已经过去的 reset 说明窗口已经恢复，而完全没有 reset 的数字不该被拿来永久停掉一个账号。

### 3.11 账号调度策略干预

**本节已按 CPA v7.3.7 的实际接口重写。** 三个关键事实：

**候选的身份是 host 的 `auth.ID`，不是 `auth_index`。** `SchedulerAuthCandidate` 只带 `ID`，CPA 不在候选上填 `auth_index`。所以路由决策必须先把 `ID` 经 `AccountRegistry.ResolveAuthID` 映射到插件的持久化键，才能查绑定表。解析不出来的候选不被偏好，但也不被排除。

**候选默认只有最高 priority 一层。** 除非注册时声明 `SchedulerAcrossPriorities`，否则 `Candidates` 只包含最高可用优先级档。插件**声明了**这个能力——因为 `state_first` 必须看到低优先级的候选才有意义。代价是 host 不再预先过滤，**优先级分档必须由插件自己算**，否则「respect_cpa_priority」会悄悄变成「不 respect 任何东西」。

**响应必须 `Handled: true` 才被采纳。** 否则 host 回退到内置调度器。这正好是「不干预」的表达方式。

```
if 总开关关闭 → Handled=false
if 状态优先开关关闭 → Handled=false
if provider 不是 codex → Handled=false
if model 未开启 TurnState → Handled=false
if 没有候选 → Handled=false

把候选的 ID 解析成 auth_index；解析失败的候选不参与偏好
A = 有有效 State 的候选
if A 为空 → Handled=false

按策略分档：
  state_first          → 在 A 内部取最高 priority 档
  respect_cpa_priority → 取全体候选的最高 priority 档，再与 A 求交；
                         若交集为空 → Handled=false（宁可不干预，也不越档）

在档内按 last_used 做 round-robin，返回 {AuthID: <candidate.ID>, Handled: true}
```

两种策略都**在单一优先级档内**做 round-robin，区别只在于这一档是在哪个集合上取的：`state_first` 在「有 State 的账号」里取，因此可能低于 host 的整体最高档；`respect_cpa_priority` 在全体候选里取，因此低档位的 State 账号**不会被跨档选中**，插件直接放弃干预。

**注册时声明的能力**（`sdk/pluginapi` → `Capabilities`）：

| 能力 | 值 | 用途 |
|---|---|---|
| `Scheduler` | true | 参与账号选择 |
| `SchedulerAcrossPriorities` | true | 拿到全部优先级档，由插件自己分档 |

### 3.12 State 自愈机制

仅当全局总开关为 ON 且本次请求确实注入了插件 State 时，才执行以下自愈规则。当使用插件注入 State 的请求出现以下错误时：

- HTTP 400 且 body 含 `previous_response_not_found` 或 routing 相关错误
- 连续 5xx

立即失效对应 `(authIndex, model)` 的绑定，可选 retry without injected state，后台重新探测。防止坏 State 在 TTL 窗口内持续污染请求。

### 4.2 插件技术选型

CPA 插件以 C-ABI 动态库（`.so` / `.dylib` / `.dll`）形式加载，通过 CGO 构建。参考现有 CPA 插件实践（如 `key-model-access`、`credit-manager`），建议技术栈：

| 层 | 选型 | 理由 |
|----|------|------|
| 插件语言 | Go (CGO c-shared) | CPA 原生插件标准 |
| 构建要求 | Go 1.24+、C 编译器、`CGO_ENABLED=1` | CPA 插件 ABI 要求 |
| 持久化 | SQLite (WAL) | 并发读写友好，适合多线程场景 |
| 管理面板 | 嵌入式 HTML + JS，通过 Resource Route 提供 | 简洁清爽的轻量前端 |
| 热路径 | 内存原子快照 | 避免请求链路查 DB |

**插件加载路径**：动态库基础 ID 必须与 CPA `plugins.configs` 中的 key 一致，产物应在目标系统上构建，不能只设置 `GOOS` 做普通交叉编译。

```sql
    last_used_at         TEXT,
    last_success         TEXT,
    last_failure         TEXT
);

-- 账号自身的模型清单（见 10.13）
-- 一行一个账号，models 是 JSON 数组：没有任何查询按元素读它，
-- 而一行一个模型需要第二张表和一次事务来维持两者一致。
CREATE TABLE account_models (
    auth_index TEXT PRIMARY KEY,
    models     TEXT NOT NULL DEFAULT '[]',
    source     TEXT NOT NULL DEFAULT '',
    synced_at  TEXT NOT NULL,
    error      TEXT NOT NULL DEFAULT ''
);

-- 调用历史（见 10.14）：一行一个被拦截的请求
-- 三个 state 列存完整值而不是前缀——这张表存在的意义就是对比它们。
CREATE TABLE call_history (
    id             INTEGER PRIMARY KEY AUTOINCREMENT,
    auth_index     TEXT NOT NULL,
    model          TEXT NOT NULL,
    request_id     TEXT NOT NULL DEFAULT '',
    carried_state  TEXT NOT NULL DEFAULT '',
    injected_state TEXT NOT NULL DEFAULT '',
    response_state TEXT NOT NULL DEFAULT '',
    status_code    INTEGER NOT NULL DEFAULT 0,
    outcome        TEXT NOT NULL DEFAULT '',
    created_at     TEXT NOT NULL
);
CREATE INDEX idx_call_history_auth    ON call_history(auth_index, created_at DESC);
CREATE INDEX idx_call_history_created ON call_history(created_at);

-- Scheduler 游标
CREATE TABLE scheduler_cursor (
    auth_index TEXT PRIMARY KEY,
    last_used  TEXT
);
```

> `proxy_cooldown`（按「账号 × 代理」记账，见 10.18）由迁移 v4 建立，此处从略。
> 当前 schema 版本为 **6**；`proxy_node.consecutive_failures` / `cooldown_until` 保留但不再读取。

**`probe_history.status_code` 的必要性。** `UPSTREAM_ERROR` 是"上游拒绝了这次请求，且不属于其他任何一类"的兜底分类，具体覆盖**全部 5xx** 加上**正文看不出是模型问题的 400/404**。在它落库之前，面板上 400（请求形状被拒）、500、503（上游不健康）长得完全一样——而这三者的应对方式不同。0 表示没有收到响应，面板按原因分别显示「无响应（网络）」「无响应（无可用代理）」「无响应（超时）」，而不是显示成 `0`——那看着像个状态码。

> `status_code` 用 `ALTER TABLE ... ADD COLUMN` 加，不需要 create/copy/drop/rename：没有删列也没有改类型，而带非空默认值意味着旧行读回 0，正是它们的真实含义——在列存在之前记录的、没有响应码的行。

### 4.4 状态持久化与启动恢复

**CPA 启动后插件状态不丢失**，所有关键状态持久化到 SQLite，插件初始化时自动恢复：

```
插件启动流程：
  1. 打开 SQLite 数据库（自动创建表结构）
  2. 执行 Schema 版本检查与迁移（见第七章）
  3. 从 settings 表恢复全局总开关、两个子开关与所有配置项，包括 probe_concurrency（默认 2）；缺失的 global_enabled 按默认值 true 初始化
  4. 从 time_windows 表恢复所有时间窗口
  5. 从 state_binding 表恢复所有有效绑定 → 重建内存快照
  6. 从 account_model_config 表恢复探测启用配置
  7. 从 proxy_node 表恢复代理节点列表、健康状态、last_used_at
  8. 从 account_models 表恢复各账号的模型清单（见 10.13）
  9. 从 scheduler_cursor 表恢复调度游标
  10. 启动 ProbeScheduler（仅当全局总开关与定时探测开关均为 ON）
  11. 注册 Management API 路由和 Resource UI
  12. 启动调用历史的异步写入器（见 10.14）与首次模型清单拉取
```

**持久化时机**：

- 全局开关变更 → 立即写入 `settings`
- 探测并发数变更 → 立即写入 `settings` 的 `probe_concurrency`
- 时间窗口增删改 → 立即写入 `time_windows`
- State 绑定变更 → 写入 `state_binding` + 追加 `state_binding_history`
- 探测完成 → 写入 `probe_history`，同时更新 `proxy_node.last_used_at`
- 代理节点状态变更 → 写入 `proxy_node`
- 内存快照在每次写入后原子更新

### 4.5 热路径设计

请求链路中 State 查询必须做到 O(1) 内存访问：

```
SQLite (持久化层)
    ↓ 写入后原子更新
Atomic Runtime Snapshot (内存)
    ↓ 请求链路只读
RequestInterceptor / Scheduler / ResponseCollector
```

内存快照使用 `sync.Map` 或 `atomic.Value` 承载不可变 map，写入时生成新 map 并原子替换。

### 4.6 关键 CPA API 依赖

| CPA API | 用途 |
|---------|------|
| `host.auth.list` / `host.auth.get_runtime` | 获取 Codex 账号列表与运行状态 |
| `host.auth.get(auth_index)` | 获取账号 credential JSON（含 access_token） |
| `RequestInterceptor` (BeforeAuth / AfterAuth) | 请求头修改、correlation 注入 |
| `ResponseInterceptor` / `StreamChunkInterceptor` | 响应头捕获 |
| Scheduler `SchedulerPickRequest` / `SchedulerPickResponse` | 读取候选信息，并返回指定 `AuthID` 或 `DelegateBuiltin` |
| Management API | 插件自有管理接口 |
| Resource Route | 提供管理面板静态资源 |

### 4.7 安全设计

- Resource Route 不经过 Management Auth，**不得**在 Resource API 直接返回 token、proxy password、完整 auth JSON。现有插件实践表明动态数据统一受管理认证保护，账号统计、检查与清理均只从 `/v0/management/...` 路由提供。
- 所有数据查询/修改操作走 Management API（`/v0/management/codex-turn-state-manager/...`）
- 管理密钥仅在浏览器页面 session 中保留，不写入插件状态、日志、localStorage

### 5.1 设计原则

### 5.5 Management API 端点

**路由改为查询参数形式。** CPA 的 Management 路由是**精确路径的 map key**（`internal/pluginhost/management.go` 的 `managementRouteKey`），并且 `normalizeManagementRoute` 会拒绝含 `:`、`*`、`..` 的路径。所以 `/bindings/{authIndex}/{model}` 这类带路径参数的路由**根本注册不上去**，动态部分必须挪到查询参数。

**管理路径是扁平的，不带 `plugins/` 段。** 宿主给插件的 `BasePath` 是 `/v0/management`，路由按 `<BasePath> + <Path>` 解析，插件段由插件自己选——没有任何地方要求它必须是 `plugins/`。不能那样选有两个原因：CLIProxyAPI 自己的插件管理接口（`/v0/management/plugins`、`/<id>/config`、`/<id>/quota`）已经占了那个子树，把插件自己的路由注册进去等于一个命名空间两个主人；而第三方管理前端按首段分类路径，CPA-Manager-Plus 把 `plugins` 列为保留段，其下的路由一律要求它自己的管理员凭证，于是注册在里面的插件在那种面板里根本够不到。它对插件用的是扁平形状（`/v0/management/codex-invite/accounts`），这也是生态里的通行做法。

资源路由正相反：host 自己插入 `/plugins/<id>`，插件不要重复。

```
GET    /v0/management/codex-turn-state-manager/status
GET    /v0/management/codex-turn-state-manager/settings
PUT    /v0/management/codex-turn-state-manager/settings
GET    /v0/management/codex-turn-state-manager/time-windows
POST   /v0/management/codex-turn-state-manager/time-windows
GET    /v0/management/codex-turn-state-manager/accounts
POST   /v0/management/codex-turn-state-manager/accounts/sync
GET    /v0/management/codex-turn-state-manager/bindings
GET    /v0/management/codex-turn-state-manager/proxy-nodes
PUT    /v0/management/codex-turn-state-manager/proxy-nodes
GET    /v0/management/codex-turn-state-manager/probe-history?limit=50
GET    /v0/management/codex-turn-state-manager/call-history?authIndex=..&limit=50&offset=0
DELETE /v0/management/codex-turn-state-manager/call-history?authIndex=..
```

动态资源走查询参数，例如删除绑定是 `DELETE /bindings?authIndex=..&model=..`，账号模型表是 `GET /accounts/models?authIndex=..`。

**`POST /accounts/sync` 有两种形态。** 不带参数是「向 CPA 重读整个账号池」；带 `?authIndex=..` 是只刷新这一个账号，再加 `&models=1` 则同时重新拉取它的模型清单（见 10.13）。面板的账号行按钮用的就是后者：在 CPA 里改完东西之后，「插件注意到了吗」是关于某一个账号的问题，而等下一次定时同步来回答它，正是让陈旧状态看起来像卡死的原因。参数里没有该账号时返回 **404** 而不是 502——那是调用方拿着一个过期的面板行，去查 CPA 的健康状况只会查错方向。

**账号模型表另有一个不带参数的批量形式**：`GET /accounts/models` 返回 `{accounts: {authIndex: [...]}}`。面板需要为每个展开的账号渲染一张表并定时刷新，逐账号请求会让刷新开销随展开数量增长，展开本身也要多等一个往返。一次请求取回全部，展开直接读缓存。

**Resource 路由同样是一文件一路由。** `ResourceRoute` 没有 method 字段（强制 GET），路径也是精确匹配，不存在静态目录或通配符。面板的 `index.html` / `app.js` / `style.css` 必须各自注册一条；只有入口文件带 `Menu` 标签，否则资源文件会被管理界面当成页面列出来。

**管理密钥可由面板自动继承。** 管理面板把会话存进 `localStorage['cli-proxy-auth']`，内容以 `enc::v1::` 前缀混淆：base64(XOR(JSON, key))，其中 XOR 密钥为 `cli-proxy-api-webui::secure-storage|<location.host>|<navigator.userAgent>`。插件页面与面板同源，因此可以直接读取并解码，无需让用户重复输入。

**前置条件：「记住密码」必须勾选。** 管理面板的持久化做了 `partialize`：

```js
partialize: e => ({
  apiBase: e.apiBase,
  ...(e.rememberPassword ? { managementKey: e.managementKey } : {}),
  ...
})
```

未勾选时 `cli-proxy-auth` 仍然存在，但**不包含 `managementKey`**，此时密钥只存在于管理面板的页面内存中，同源 iframe 也读不到。面板因此必须区分三种情况并给出可操作的提示，而不是一律弹登录框：

| 情况 | 提示 |
|---|---|
| 无 `cli-proxy-auth` | 未检测到管理面板会话，请手动输入 |
| 有会话但无密钥 | 提示登录管理面板时需勾选「记住密码」 |
| 有密钥但无法解码 | 提示 CPA 可能更改了存储格式，请手动输入 |

该格式**不是公开契约**，是从管理前端产物里读出来的，并对照了另一个真实插件的实现。因此插件的解码必须容错：格式变化或解码失败时退回手动输入，而不是卡住。

**插件只读不写**：密钥由 CPA 管理面板自行决定是否持久化，本插件不把它写入任何存储。

**面板样式的 `[hidden]` 必须全局强制生效。** 作者样式里的 `display` 声明优先级高于浏览器默认的 `[hidden] { display: none }`，所以 `.gate { display: flex }` 这类规则会让设置了 `hidden` 属性的元素照样显示。本插件曾因此让登录框一直盖在正常工作的面板上方，而 DOM 的 `.hidden` 属性读出来是 `true` —— 所有程序化检查都报告正常。样式中只有一条全局的 `[hidden] { display: none !important; }`，不得再添加针对单个选择器的 `[hidden]` 规则。

| **P0 — 探测引擎** | ProbeScheduler + TimeWindowManager + ProbeExecutor（含遍历所有代理直到命中目标），探测并发数默认 2 且可配置 | 可对指定 `(账号, 模型)` 发起定时探测 |
| **P0 — 请求拦截** | CorrelationManager + RequestStateInjector + ResponseStateCollector | 请求头替换与响应头反向绑定全链路打通 |
| **P0 — 全局开关** | 定时探测开关 + 反向绑定开关，独立控制，状态持久化 | 两个开关可独立启停 |
| **P0 — 绑定管理** | 绑定删除 + 历史记录 + Management API | 面板可删除绑定并查看历史 |
| **P1 — 调度干预** | CredentialScheduler | CPA 调度结果可被插件干预 |
| **P1 — 管理面板** | ResourceUI：简洁前端 + 时间窗口配置 + 历史弹窗 + 代理池展示 + 探测并发配置 | 可视化操作全部功能 |
| **P1 — 自愈与退避** | State 失败自动失效、探测退避策略、被动续期 | 系统具备自愈能力 |
| **P2 — 可观测性** | 探测历史查询、代理健康统计、State 状态可视化 | 运维面板完善 |

### 6.2 关键里程碑与风险

| 里程碑 | 风险点 | 缓解措施 |
|--------|--------|----------|
| 请求拦截 correlation 机制验证 | CPA RequestInterceptor 在 AfterAuth 阶段是否保留自定义 header | 开发前先验证 header 传递链路 |
| 流式响应头捕获 | `StreamChunkInterceptor` 的 `HeaderInitIndex = -1` 行为 | 参考 `jshandler` 插件的拦截器实现 |
| 代理遍历耗时控制 | 单次探测遍历多个代理可能超过并发槽位占用时间 | 设置 `maxProbeDuration` 上限，超时立即终止 |
| 探测并发数控制 | 并发过高导致上游限流或本地资源紧张 | 默认 2，可配置，配合 jitter 与退避 |
| 代理 `last_used_at` 并发写入 | 多个 worker 同时更新可能产生竞争 | SQLite WAL + 单条 UPDATE；内存中维护代理使用时间快照 |
| CGO 跨平台构建 | `c-shared` 产物需在目标系统上构建 | 各平台分别构建，使用 CI 矩阵 |
| Turn-State 协议兼容性 | OpenAI 可能更改 turn-state 语义或长度 | 目标长度可配置，非目标长度只记录不绑定 |
| 时间窗口跨天处理 | 如 22:00–06:00 的窗口判定 | 实现时需处理跨天逻辑，单独测试 |
| SQLite 迁移失败 | 迁移中途崩溃导致半迁移状态 | 迁移前备份 + 事务保护 + 中断恢复机制 |

### 6.3 测试策略

- **单元测试**：StateRegistry 状态转换、退避策略计算、代理选择排序（冷却最久优先）、时间窗口判定（含跨天）、每个迁移函数、探测并发数配置读取
- **集成测试**：在模拟 CPA 环境中验证 correlation 全链路、Scheduler 干预、响应捕获、持久化恢复
- **仿真测试**：对探测调度、退避、绑定生命周期、代理遍历逻辑进行状态机仿真；模拟多个代理节点部分故障场景；验证 `maxProbeConcurrency=2` 时队列按槽位执行
- **持久化与迁移测试**：验证 CPA 重启后所有状态正确恢复；验证从 v1 依次迁移到最新版数据完整性；模拟迁移中途失败验证自动恢复备份

## 七、数据库版本管理与升级迁移

### 7.1 设计目标

| 目标 | 说明 |
|------|------|
| 自动迁移 | 插件加载时自动检测数据库版本，按顺序执行迁移，无需人工干预 |
| 数据不丢失 | 迁移前强制备份，迁移失败可恢复 |
| 幂等安全 | 每个迁移只执行一次，重复启动不会重复应用 |
| 可回滚 | 保留备份文件，支持手动回滚到旧版本 |
| 向前兼容 | 新插件可读旧数据库；旧插件遇到新数据库时拒绝启动而非损坏数据 |
| 可审计 | 记录每次迁移的版本、时间、校验和 |

### 7.2 版本管理机制

#### 7.2.1 Schema 版本表

不使用 `PRAGMA user_version`，而是使用独立表 `schema_migrations`，便于记录迁移历史与校验和。业界实践表明 `PRAGMA user_version` 存在不可靠的情况，使用独立表更为稳妥。

```sql
CREATE TABLE IF NOT EXISTS schema_migrations (
    version     INTEGER PRIMARY KEY,
    name        TEXT NOT NULL,
    checksum    TEXT NOT NULL,
    applied_at  TEXT NOT NULL DEFAULT (datetime('now'))
);
```

- `version`：递增整数，从 1 开始。
- `name`：迁移名称，如 `init`、`add_last_used_at`。
- `checksum`：迁移脚本内容的 SHA-256，防止代码中迁移被意外修改。
- `applied_at`：应用时间。

#### 7.2.2 当前代码期望版本

插件代码中定义：

```go
const CurrentSchemaVersion = 3 // 每次新增迁移时递增
```

启动时比较数据库版本与 `CurrentSchemaVersion`：

| 数据库版本 | 代码版本 | 行为 |
|------------|----------|------|
| 0（空库） | 3 | 创建所有表，依次执行迁移 1→3，标记为 3 |
| 1 | 3 | 执行迁移 2、3 |
| 3 | 3 | 无需迁移 |
| 4 | 3 | **拒绝启动**，提示数据库版本高于插件支持版本 |

### 7.3 迁移流程

```
插件启动
  │
  ▼
打开 SQLite（WAL 模式）
  │
  ▼
确保 schema_migrations 表存在
  │
  ▼
读取当前数据库版本 dbVersion
  │
  ├── dbVersion > CurrentSchemaVersion → 拒绝启动，记录错误日志
  │
  ├── dbVersion == CurrentSchemaVersion → 跳过迁移
  │
  └── dbVersion < CurrentSchemaVersion
        │
        ▼
      执行迁移前检查：
        1. 检查是否存在未完成的迁移标记（migrating 状态）
        2. 若存在，尝试从最近备份恢复
        3. 若无法恢复，拒绝启动
        │
        ▼
      备份数据库（VACUUM INTO）
        │
        ▼
      对每个待执行迁移 m（按 version 升序）：
        │
        ├── 开启事务
        ├── 执行 m.Up(tx)
        ├── 校验 m.Checksum
        ├── 写入 schema_migrations
        ├── 提交事务
        └── 失败 → 回滚事务 → 恢复备份 → 拒绝启动
        │
        ▼
      迁移完成，更新内存版本号，继续初始化
```

### 7.4 迁移脚本管理

#### 7.4.1 迁移定义

以下代码包含版本 1–3 的当前迁移，以及一个**未来版本示例**。版本 4 示例只有在正式发布该迁移并同步更新 `CurrentSchemaVersion` 后才能启用。迁移以有序切片定义在 Go 代码中，每个迁移包含版本、名称、Up 函数：

```go
type Migration struct {
    Version  int
    Name     string
    Up       func(tx *sql.Tx) error
}

var migrations = []Migration{
    {
        Version: 1,
        Name:    "init",
        Up: func(tx *sql.Tx) error {
            // 创建 settings、time_windows、account_model_config、
            // state_binding、state_binding_history、probe_history、
            // proxy_node、scheduler_cursor 等表
            return nil
        },
    },
    {
        Version: 2,
        Name:    "add_proxy_last_used_at",
        Up: func(tx *sql.Tx) error {
            _, err := tx.Exec(`ALTER TABLE proxy_node ADD COLUMN last_used_at TEXT`)
            return err
        },
    },
    {
        Version: 3,
        Name:    "add_probe_history_index",
        Up: func(tx *sql.Tx) error {
            _, err := tx.Exec(`CREATE INDEX IF NOT EXISTS idx_probe_history_auth_model
                               ON probe_history(auth_index, model, probed_at DESC)`)
            return err
        },
    },
}
```

#### 7.4.2 迁移校验和

每个迁移在代码中计算其 `Up` 函数内容的 SHA-256（或迁移 SQL 文本的 SHA-256），写入 `schema_migrations.checksum`。启动时若发现已应用迁移的 checksum 与当前代码不一致，拒绝启动并提示“迁移脚本被修改，请检查”。迁移工具如 `golang-migrate` 使用校验和检测已应用脚本的变更，`gostgrator` 也支持在运行 up 迁移前比较 MD5 哈希。

#### 7.4.3 未来迁移示例：重建表

以下 Version 4 仅用于说明 SQLite 重建表方式，不属于当前迁移切片。正式启用前必须将 `CurrentSchemaVersion` 更新为 4，并将该迁移加入有序迁移列表。

SQLite 不支持直接删除列或修改列类型，需要重建表：重命名旧表、创建新表、复制数据、删除旧表、重命名新表。例如将 `proxy_node` 的 `url` 字段改为 `endpoint`：

```go
{
    Version: 4,
    Name:    "rename_proxy_url_to_endpoint",
    Up: func(tx *sql.Tx) error {
        // 1. 创建新表
        _, err := tx.Exec(`
            CREATE TABLE proxy_node_new (
                id                   TEXT PRIMARY KEY,
                endpoint             TEXT NOT NULL,
                enabled              INTEGER NOT NULL DEFAULT 1,
                success_count        INTEGER NOT NULL DEFAULT 0,
                failure_count        INTEGER NOT NULL DEFAULT 0,
                consecutive_failures INTEGER NOT NULL DEFAULT 0,
                cooldown_until       TEXT,
                last_latency_ms      INTEGER,
                last_used_at         TEXT,
                last_success         TEXT,
                last_failure         TEXT
            )`)
        if err != nil { return err }

        // 2. 复制数据
        _, err = tx.Exec(`
            INSERT INTO proxy_node_new
                (id, endpoint, enabled, success_count, failure_count,
                 consecutive_failures, cooldown_until, last_latency_ms,
                 last_used_at, last_success, last_failure)
            SELECT id, url, enabled, success_count, failure_count,
                   consecutive_failures, cooldown_until, last_latency_ms,
                   last_used_at, last_success, last_failure
            FROM proxy_node`)
        if err != nil { return err }

        // 3. 删除旧表
        _, err = tx.Exec(`DROP TABLE proxy_node`)
        if err != nil { return err }

        // 4. 重命名新表
        _, err = tx.Exec(`ALTER TABLE proxy_node_new RENAME TO proxy_node`)
        return err
    },
},
```

整个重建过程必须在同一个事务中完成。

### 7.5 备份与恢复

#### 7.5.1 备份策略

- **时机**：每次执行迁移前，自动备份。
- **方式**：使用 SQLite `VACUUM INTO 'backup_path'`，生成一致性快照，兼容 WAL 模式。
- **路径**：`plugin-data/codex-turn-state-manager/backups/state.db.v{fromVersion}.{timestamp}.bak`
- **保留**：默认保留最近 5 个备份，超出后按时间删除最旧。
- **记录**：备份完成后，在 `settings` 表写入 `last_backup_path` 与 `last_backup_at`。

#### 7.5.2 恢复流程

当迁移失败或用户手动回滚时：

1. 关闭数据库连接。
2. 将备份文件复制回 `state.db`。
3. 删除 `state.db-wal` 和 `state.db-shm`（若存在）。
4. 重新打开数据库。
5. 记录恢复日志。

#### 7.5.3 迁移中断保护

在开始迁移前，向 `settings` 表写入：

```
migration_state = 'migrating'
migration_from_version = dbVersion
migration_to_version = CurrentSchemaVersion
migration_started_at = now
```

迁移全部成功后清除该状态。若启动时发现 `migration_state = 'migrating'`，说明上次迁移中断，自动尝试从最近备份恢复，并提示用户。WAL 模式下，如果崩溃发生在写入过程中，SQLite 会在下次引擎初始化时利用 WAL 文件回滚未提交的事务。

### 7.6 兼容性策略

#### 7.6.1 向前兼容（新插件读旧库）

通过上述迁移机制保证。新插件启动时自动将旧库升级到最新结构。

#### 7.6.2 向后兼容（旧插件读新库）

旧插件不支持新表结构。策略：

- 旧插件启动时读取 `schema_migrations` 最大版本。
- 若数据库版本 > 旧插件 `CurrentSchemaVersion`，**拒绝启动**，并输出明确错误：
  ```
  数据库版本 (4) 高于当前插件支持版本 (3)。
  请升级插件，或从备份恢复旧数据库。
  ```
- 不尝试降级，避免数据损坏。

#### 7.6.3 回滚插件版本

若用户需要回滚插件到旧版本：

1. 停止 CPA。
2. 从 `backups/` 目录选择对应旧版本的备份文件。
3. 替换 `state.db`。
4. 安装旧版插件并启动。

插件面板可提供“备份管理”入口，列出可用备份，支持下载与恢复。

### 7.7 开发规范

| 规范 | 说明 |
|------|------|
| 每次修改表结构必须新增迁移 | 不得修改已发布的迁移脚本 |
| 迁移版本号严格递增 | 不允许跳号或重复 |
| 迁移必须可重入 | 使用 `IF NOT EXISTS`、`IF EXISTS`，但版本控制仍为主 |
| 迁移必须在事务中 | 除 `VACUUM` 等特殊操作外，所有 DDL/DML 均在事务内 |
| 迁移前必须备份 | 由 PersistenceManager 统一执行，迁移函数内不自行备份 |
| 迁移失败必须回滚并恢复 | 不允许留下半迁移状态 |
| 新增列必须提供默认值 | 避免旧数据读取时 NULL 异常 |
| 索引变更也走迁移 | 保证所有环境一致 |
| 迁移日志写入独立日志表 | 便于排查 |

### 7.8 测试要求

- **单元测试**：每个迁移函数在内存 SQLite 中执行，验证前后结构一致。
- **迁移链测试**：从 v1 依次迁移到最新版，验证数据完整性。
- **失败注入测试**：模拟迁移中途失败，验证自动恢复备份。
- **并发测试**：多个 goroutine 同时启动时，迁移只执行一次（启动阶段单线程，天然满足）。
- **版本过高测试**：数据库版本高于代码版本时，验证拒绝启动逻辑。
- **备份恢复测试**：验证 `VACUUM INTO` 备份可正确恢复，WAL 文件清理干净。

## 九、文档审查结论与开发前待确认事项

本轮调查基于当前工作区文档和已有设计进行。工作区未包含 CPA 源码、插件 SDK、`key-model-access`/`jshandler` 示例或可运行的 CPA 实例，且当前环境无法访问外部代码仓库，因此涉及 CPA 具体回调行为的事项不能仅凭推断标记为已确认。

### 9.1 已确认并已落地

1. **字段命名约定**：统一使用 `authIndex` 作为插件持久化和 State 主键；使用 `AuthID` 作为 CPA Scheduler 的运行时标识；AccountRegistry 必须维护二者映射。数据库列名继续使用 `auth_index`。
2. **时间窗口语义**：`daysOfWeek` 为空表示每天；跨天窗口按当天晚间到次日凌晨处理。第 3.4 节伪代码已覆盖这两种情况。
3. **总开关并发语义**：关闭总开关后，新请求立即旁路；已经发出的探测请求可以自然结束，但返回结果必须丢弃，不能写入绑定。该规则已写入第 3.3 节，并通过 NF-10 要求原子化读取。
4. **迁移版本示例**：第 7.4 节的版本 4 已标注为未来迁移示例，当前 `CurrentSchemaVersion = 3` 不变。
5. **自愈边界**：只有总开关开启且请求确实注入了插件 State 时才执行失效和重试，已写入第 3.12 节。

### 9.2 仍需在 CPA 实例或源码中验证

1. **请求拦截器的 header 传递链路**：验证 BeforeAuth 写入的 correlation 是否能被 Scheduler 和 AfterAuth 读取，以及 AfterAuth 是否允许清理并替换 `X-Codex-Turn-State`。
2. **Scheduler 返回值**：验证 `SchedulerPickResponse` 是否确实支持返回指定 `AuthID`，并确认候选列表中的标识与 `host.auth.list` 返回值如何对应。
3. **流式响应头回调**：验证 `StreamChunkInterceptor` 的 `HeaderInitIndex = -1` 是否稳定提供初始响应头，以及回调时能否取得 RequestID、AuthID 和 Model。

建议的验证顺序是：先用最小插件验证 header 在 BeforeAuth → Scheduler → AfterAuth 的流转，再验证 Scheduler 指定账号，最后验证流式响应头回调。上述验证完成前，不应把相关能力标记为生产可用。

## 十、与 CPA v7.3.7 的对齐记录

本章记录文档与真实 CPA 源码核对后的结论。核对对象为 `github.com/router-for-me/CLIProxyAPI` **v7.3.7**（commit `b773607`，2026-09-18 main）。文档其余章节若与本记录冲突，以本记录为准。

### 10.1 已由源码确认的结论

| # | 原假设 | 核对结果 | 影响 |
|---|---|---|---|
| 1 | AfterAuth 不暴露 AuthID，需用 correlation header 关联 | 前半句成立，但 conductor 会在钩子调用前写入 `selected_auth_id` / `selected_auth_index` 到 `Metadata` | correlation 机制整体移除，少一个拦截阶段 |
| 2 | `SchedulerPickResponse` 支持指定账号 | 支持：`{AuthID, DelegateBuiltin, Handled}`，`AuthID` 必须精确匹配候选 `ID`，且 `Handled` 必须为 true | 路由干预可行 |

### 10.5 真实加载暴露的两个宿主约束

这两条都是「插件侧毫无报错、功能静默失效」的类型，各花了一轮才定位：

| 约束 | 表现 | 正确做法 |
|---|---|---|
| `validPlugin` 要求 `Name` / `Version` / **`Author`** / `GitHubRepository` 全部非空 | 缺 `Author` 时宿主打印 `returned invalid metadata or no capabilities`，然后**丢弃全部能力声明**——插件加载成功但永远不会被调用 | 四项都填满，并有测试锁定 |

### 10.6 第三个宿主约束：`management.handle` 同时承载资源请求

宿主的 Resource 路由与 Management 路由**共用同一个 `management.handle` RPC 方法**，插件必须按路径分支。

最初的桥接实现把资源请求也送进了插件的管理 mux（挂在 `/v0/management/plugins/<id>` 下），资源路径匹配不到任何路由，于是返回 404——而宿主侧 `ServeResourceHTTP` 返回 true、日志显示分发成功，**插件侧也没有任何报错**。表现就是面板打不开而管理 API 一切正常。

诊断方法：构建一个带调试日志的 CPA（在 `pluginResourceNoRoute` 与 `ServeResourceHTTP` 打点）后，日志显示 `ServeResourceHTTP=true`，据此才能确定是插件返回了 404 而不是宿主没分发。

> 记录一次误判：最初用 CPA 自带的 `examples/plugin/management-api` 做对照，结论是「宿主侧问题」。该结论**是错的**——对照实验里 `.so` 被命名为 `example-management-api.so`，插件 id 因此是 `example-management-api`，而请求用的是 `example-management-api-go`，id 不匹配才导致 404。对照实验的两个变量没有对齐，结论无效。

### 10.7 模型清单：插件读不到，因此不能猜

插件**无法获知某个账号有哪些模型**。host 侧虽然有全局模型注册表（`registry.GetGlobalRegistry().GetModelsForClient`），但只通过管理 API 的 `/v0/management/auth-files/models` 暴露，而插件没有任何回调可以读它。

最初的实现把插件内置的能力表直接当成账号的模型列表，于是面板上显示出 `gpt-5-codex`、`gpt-5-mini` 这些**早已不存在的模型名**，看上去像事实，实际是猜测。

**修正后的分工**：

| 数据 | 归属 |
|---|---|
| `(账号, 模型)` 列表——哪些 pair 要探测 | **运维配置**，持久化在 `account_model_config`；面板只显示已配置的 |
| 每个模型的 reasoning 下限——探测请求用什么级别 | 插件内的能力表，但不作为模型是否存在的事实 |
| 建议模型名 | 插件内置种子表，仅作为「添加」控件的候选项 |

种子表取自 **CPA 自己同步的那份清单**（`github.com/router-for-me/models` 的 `codex_client_models.json`），当前为 `gpt-6-astra` / `gpt-5.6-sol` / `gpt-5.6-terra` / `gpt-5.6-luna` / `gpt-5.5` / `gpt-5.3-codex-spark`，全部模型的最低推理级别均为 `low`。表过期只影响候选项，不再影响事实。

未知模型名落到兜底能力（`low`），因此运维手工添加任意模型名都能发出合法探测请求；账号是否真的支持它，由探测结果（`MODEL_UNSUPPORTED`）回答，而不是由插件的表回答。

### 10.8 真实链路验证

**探测链路已端到端跑通**（真实 Codex 账号 + 真实代理）：

```
SUCCESS_TARGET  len=292  1727ms
绑定：fresh, len=292, source=probe, proxy=local-7890, 剩余 3588s
下次探测：+51 分钟（= TTL × 85%，退避正确）
代理统计：ok=1 fail=0
```

覆盖环节：调度器扫描 → 选中到期 pair → 遍历代理池 → 实时获取凭证 → 构造探测请求 → 经代理访问上游 → 读取 `X-Codex-Turn-State` → 命中目标长度绑定 → 写入内存快照 → 排定下次探测。

**过程中发现并修复了一个致命缺陷**：适配层把注册的超时 context 传给了 `App.Start`，`defer cancel()` 在注册返回时立即触发，导致**扫描循环当场退出**。管理 API 是请求驱动的所以一直正常响应，掩盖了「后台什么都没跑」这一事实。已改为 `App.Start()` 不接收 context——插件生命周期归插件自己所有，由 `plugin.shutdown` 结束。回归测试通过「注入缺陷 → 测试必须失败」验证过其有效性。

### 10.9 目标长度确认：312 不是目标值

对同一账号实测五个模型（真实上游、真实代理）：

| 模型 | 结果 | State 长度 |
|---|---|---|
| gpt-5.5 | SUCCESS_TARGET | 292 |
| gpt-5.6-luna | SUCCESS_TARGET | 292 |
| gpt-5.6-terra | SUCCESS_NON_TARGET | **312** |
| gpt-5.6-sol | MODEL_UNSUPPORTED | 0 |
| gpt-6-astra | MODEL_UNSUPPORTED | 0 |

结论：

1. **312 不是目标值，不可跨 turn 复用**（已确认）。因此 `target_state_length` 保持单一全局值 292 是正确的，terra 返回的 312 被 F-15 正确拒绝绑定，行为符合规范。
2. **`MODEL_UNSUPPORTED` 判定有效**：sol 与 astra 确实不被该账号支持，插件从响应体正确识别，并按 30 分钟退避。

**连带后果**：持续返回非目标长度的 pair 会按 SUCCESS_NON_TARGET 每 2–5 分钟重试一次，且永远不会有结果。这是设计规定的退避，不应擅自更改；改为**把连续非目标次数暴露到面板**（`nonTargetStreak`），由运维判断该模型不值得探测并自行关闭。不自动禁用——设计文档只允许对 `MODEL_UNSUPPORTED` 自动禁用。

模型清单自动获取后，五分之二不可用属于正常范围——清单来自套餐级别的目录，插件无法读取单账号的实际集合，由探测回答。

### 10.10 账号套餐类型

面板显示账号套餐（Free / Plus / Pro / Team …）。数据来自 **`id_token` 的 `chatgpt_plan_type` claim**，与 CPA 自身读取的来源一致：

```
id_token → base64url(payload) → ["https://api.openai.com/auth"]["chatgpt_plan_type"]
```

同时读取 `chatgpt_subscription_active_until` 作为续期时间。**不校验签名**——该 token 由 CPA 签发并已验证过，这里只是读一个展示属性，不做信任决策。

**该 claim 并非所有账号都有**：实测账号的 id_token 与 access_token 都不含 `chatgpt_plan_type`（CPA 对它也只能用 Pro 档兜底）。因此缺失时面板**不显示徽章**，而不是显示「未知」——否则只包含该字段的账号会让面板充满噪音。未识别的取值**原样显示**，不做映射：为一个没见过的值编造一个更好看的名字，等于把猜测当事实，模型列表已经犯过一次这个错。

读取时机：**每个账号每个进程一次**。计划很少变，重启即刷新；凭据文档用完即弃，不留存、不落库、不写日志（NF-06）。

**不要把 `HostAuthFileEntry.AccountType` 当成套餐。** SDK 里有这个字段，名字也像，但实测值是 `oauth`——它是凭据种类（OAuth 还是 API key），不是订阅档位。把它接到套餐徽章上，面板会把每个账号都显示成「oauth」。同样是实测：SDK 的 `QuotaProvider` 是插件**实现**给管理端看的接口，host 侧没有对应的读取方法（`host.*` 方法只有 http/model/stream/log/auth/affinity 六类），所以套餐与额度都只能来自凭据 claim 和上游响应头这两个来源，没有第三条路。

**套餐与额度必须跨 `Sync` 保留。** `Sync` 是按宿主的账号列表重建整张表的，而那份列表既不含套餐也不含额度——两者都是插件自己从上游响应头学到的。早先的实现只把 `Plan` 继承了下来、漏了 `Quota`，后果是每 5 分钟一次的同步把额度徽章清空一次，而套餐留着：看起来像「额度本来就没有」，而不像「被覆盖了」。新增 `Account` 上这类「由插件自己填充、宿主不提供」的字段时，都要在 `Sync` 的继承列表里加上，否则默认就是每次同步丢一次。


### 10.11 账号可探测判定：只拒绝探测不可能成功的状态

`host.auth.list`（`HostAuthFileEntry`）给出判定所需的全部字段：

| 字段 | 含义 |
|---|---|
| `disabled` / `status=disabled` | 账号被禁用 |
| `unavailable` | 上游临时不可用，CPA 注释写的是 "e.g. quota exceeded" |
| `next_retry_after` | CPA 认为最早值得重试的时刻 |
| `status_message` | CPA 自己的解释，如具体的限额原因 |
| `status` | `active` / `pending`（等 MFA）/ `refreshing` / `error` / `unknown` |

**判定规则**（`accounts.Judge`）只有一条：**探测不可能成功的状态才拒绝探测**。

| 情形 | Kind | 是否停止探测 |
|---|---|---|
| CPA 已不再列出该账号 | `deleted` | 是 |
| `disabled` 或 `status=disabled` | `disabled` | 是 |
| `status_message` 含 401 / 403 / unauthorized / revoked 等 | `auth` | 是 |
| `status=pending`（等 MFA） | `pending` | 是 |
| `status=refreshing` | `refreshing` | 是 |
| `unavailable`、`next_retry_after` 未到、`status=error`、429、503 | `cooldown` | **否** |
| `status=unknown` 或空 | `ok` | 否 |

**为什么把「临时冷却」排除在停止条件之外。** CPA v7.3.7 里 `unavailable` / `next_retry_after` / `StatusError` 是**同一段代码**写下的（`conductor_cooldown.go` 的 `applyCooldownRecord`），触发条件就是额度耗尽和限流——注释里写着 "temporarily unavailable due to errors"。也就是说，把这三个字段当作停止条件，等于**专门在限流时停止探测**，而这正是最该继续探测、好知道它什么时候恢复的场景。

这个错误在真实环境里表现为：运维在 CPA 里刷新了账号、账号已经可用，插件面板却一直挂着「已暂停探测」。两个原因叠加：

1. 判定过宽，把 CPA 的临时冷却当成了停止条件；
2. **账号同步被开关和时间窗口挡在后面**。原来的 `Scheduler.Scan` 在 `!caps.Probe` 和 `ShouldProbeNow()` 两处提前 return，而账号同步写在它们之后——所以窗口之外（或关闭探测时）插件再也没问过 CPA，账号状态就冻结在上次窗口内的样子。现已把同步移到所有闸门之前：它只是读一次 CPA 的账号列表，不是探测。

**探测前的实时状态检查。** `Scheduler.Scan` 在决定探测谁之前，会对本轮涉及的每个账号调用一次 `SyncAccount`：这是设计要求里的「每次探测时同步获取最新状态」。**按账号一次，而不是按 pair 一次**——一个账号下的多个模型问的是同一个问题。CPA 回答里没有该账号时，`Forget` 会连带清掉它的模型清单、探测开关和绑定：留着绑定会让插件继续往请求里塞一个再也无人维护的 State 值。

**「问不到」不等于「已消失」。** `ListAccounts` 报错时保留缓存视图并照常探测。反过来处理会因为在一次宿主抖动里删掉健康账号的全部绑定，而这是不可恢复的——重建它们的那次探测刚好被跳过了。

**账号不会从面板消失**（除非 CPA 真的删了它），只是标注原因。面板的措辞也按判定分开：只有真正停止探测时才写「已暂停探测」，临时冷却写「限流冷却」，并在展开区说明「仍在探测」。

**按账号拉取模型清单。** 见 10.13。

> 顺带修正一处常量错误：此前把「可用」写成 `available`，而 CPA 用的是 **`active`**。mock 与插件一致地写着错值，所以测试全绿——真实实例才会暴露。现已按 CPA 的取值对齐，并补齐 `pending` / `refreshing` / `error` / `unknown`。

### 10.12 上游响应头：反向绑定的现状与意外收获

对真实流量实测（`/v1/chat/completions` → CPA 翻译 → Codex 执行器），header-init 回调收到的响应头经快照确认为 **28 个**，其中：

| 头 | 是否出现 |
|---|---|
| `X-Codex-Turn-State` | **否** |
| `X-Codex-Plan-Type` | 是 |
| `X-Codex-Primary-Used-Percent` / `-Reset-At` / `-Window-Minutes` | 是 |
| `X-Codex-Secondary-*` | 是 |
| `X-Codex-Credits-Balance` / `-Unlimited` / `-Has-Credits`、`X-Codex-Active-Limit` | 是 |

**结论一：反向绑定在这条路径上不生效，且原因不在插件侧。** 响应头 map 非空（28 个），插件的读取逻辑无误，是上游不在这条链路上返回 turn-state。相比之下**主动探测稳定能拿到 292 长度的 state**，两者差别在请求形态：探测是直连上游的最小化请求，业务流量是经 CPA 翻译的真实 turn。

**已接受该限制**（运维决定）：反向绑定是降低探测频率的优化，不是核心能力。核心链路「探测 → 绑定 → 注入」已全部验证通过。若将来要追查，方向是对比两种请求形态下上游的原始响应，从 CPA 侧确认转发是否丢弃该头。

**结论二：上游在响应头里直接给出账号的套餐与额度状态**，而 CPA 不向插件暴露这两者：

- `X-Codex-Plan-Type` —— 套餐类型。**比 `id_token` 的 `chatgpt_plan_type` claim 可靠**：实测账号的 token 里根本没有该 claim，上游却每个真实响应都给。
- `X-Codex-Primary-*` —— 5 小时窗口的使用率、重置时刻、窗口长度。
- `X-Codex-Secondary-*` —— 周窗口的同组字段。

插件在**流量路径**解析这些头（探测路径的最小化请求拿不到它们），据此在面板展示套餐与额度徽章。

解析必须容错：这些头没有文档、可能随时增删改形，因此缺失或解析失败一律留空，**绝不能让携带它的那个响应因此失败**。

### 10.13 模型清单按账号拉取并持久化

原先的模型清单是**所有账号共用一份**（CPA 同步的那份 manifest，是所有套餐的并集）。这对任何一个具体账号都是过度近似：Team 账号和 Plus 账号的清单并不相同，并集对两者都是错的。

插件改用 Codex 客户端自己的接口按账号拉取：

```
GET https://chatgpt.com/backend-api/codex/models?client_version=<ver>
Authorization: Bearer <access_token>
Originator: codex_cli_rs
Chatgpt-Account-Id: <account_id>   （可选）
```

响应形如 `{"models":[{"slug":"..."}, ...]}`，取 `slug`（`id` 作为兼容回退）。

**何时拉取。** 这是一次消耗该账号自身额度的请求，所以只在两处发生：账号**第一次**出现在插件里时（`app.loadMissingModels`，启动后与第一次同步之后各跑一次，之后每 3 分钟补一轮漏网的），以及运维**手动点「同步」**时。除此之外不再重读。

**拉取失败不清空已有清单。** 失败会记在清单条目上（`account_models.error`）并保留原清单——过期清单比空清单有用，而面板会说明「清单是旧的，因为上次刷新失败」，而不是把旧数据当新的展示。

**兜底。** 尚未拉取成功（或宿主无外网）时回退到共用 manifest。面板会明确标注「共用清单（兜底）」，因为两者长得一模一样，而兜底那份包含该账号可能并不提供的模型。

**账号消失时连带删除。** `DeleteModelList` 同时删掉 `account_model_config` 里该账号的探测开关：两张表用同一个 pair 作键，留着开关会让账号一旦回归就静默恢复探测。

### 10.14 调用历史

每个被拦截的请求记一行，把三处回调各自看到的三分之一拼起来——这三个事实分散在注入器、响应拦截器和宿主的完成回调里，除此之外只能靠对日志：

| 列 | 来源 |
|---|---|
| `carried_state` | 注入**之前**请求里已有的 State 值（客户端带的，或上层留下的） |
| `injected_state` | 插件写入的值；为空即「未注入」 |
| `response_state` | 上游响应头里的 State 值；为空即「未返回」 |
| `status_code` | 宿主完成回调给出的上游 HTTP 状态 |
| `outcome` | 宿主的终态：`succeeded` / `failed` / `rejected` / `canceled` |

**请求路径不碰 SQLite（NF-01）。** 记录在内存里按 request id 组装，完成时经一个有界 channel 交给后台写入器批量入库（`callhistory.Recorder`）。channel 满时**丢行而不是阻塞**——这段代码跑在服务用户请求的 goroutine 上。丢弃计数和写入错误都上报到 `/status` 的 `callLog`，面板因此能解释历史里的空洞，而不是让它看起来像「没有流量」。

**只有 `Complete` 会落行。** 流式路径的 header-init 回调在回合还在进行时就到了，在那里写会产生两行。另外 `Sweep` 会给超过 15 分钟仍未走到终态的记录补一行（`status_code=0`），否则取消掉的请求会永远留在内存里。

**容量上限 24 小时。** 一条记录含三个完整 State 值，表的增长跟流量走而不是跟时间走；它回答的问题（「这个请求带了什么、返回了什么」）是关于最近几分钟的。设置项 `call_history_retention_hours` 默认 24、上限也是 24。

**开关归属。** 调用历史由**全局总开关**单独把守，不受三个子开关影响。理由是它回答的是「插件对我的请求做了什么」——这正是运维在关掉某个能力时最想问的问题。总开关关闭时插件不记录任何东西。

**面板侧**：账号行的「调用历史」按钮打开弹框，分页在弹框页脚（放在滚动区末尾的话，要翻页得先滚过它控制的那 50 行）。列表只显示 State 前 8 位：整值每个 300 字符、一页 50 行就是 45 KB 的密钥随每次轮询下发，而面板要回答的是结构性问题（注入了没有、上游回没回、状态码多少），前缀加长度就够了。

### 10.15 尚未验证

**请求注入已由真实业务流量验证**：经 CPA 的请求确实带上了注入的 `X-Codex-Turn-State`，`unresolvedAuth` 与 `noBinding` 均为 0。

**仍未验证的是 `request.complete` 与自愈。** `pluginabi.handleCompletion` / `app.ObserveCompletion` 覆盖率为 0，也尚未在真实流量中观察到触发；自愈（§3.12）正挂在这个回调上，要等一次真实的失败请求才会走到。非流式路径（`pluginabi.handleResponseIntercept` / `Collector.ObserveResponse`）同样是 0——至今所有真实流量都是 SSE 流式。

**响应反向捕获在这条链路上不生效**，见 §10.12：响应到达插件时有 28 个响应头，其中没有 `X-Codex-Turn-State`。

### 10.16 插件商店：产物形状是契约，不是约定

CPA 内置插件商店（`internal/pluginstore`）。用户在 `plugins.store-sources` 里加一条 registry.json 的 URL，商店就会列出其中的插件并一键安装。官方 registry 始终包含在内，`store-sources` 只是追加。

**两种安装类型**：registry 条目省略 `install` 时默认 `github-release`——商店去读 `repository` 指向仓库的最新 release，并从 tag 推导版本；`direct` 则在 registry 里逐平台写死 `url` + `sha256`。两条路径都把产物当成 **zip** 下载。

**命名是精确匹配，不是模式匹配。** `SelectReleaseAssets` 按字符串查找资产名，`readTargetLibrary` 按字符串校验库名：

| 规则 | 值 |
|---|---|
| 资产名 | `<id>_<version>_<goos>_<goarch>.zip` |
| 版本 | tag 去掉前导 `v`：`v0.1.0` → `0.1.0` |
| `checksums.txt` | 同一 release 中**必需**，缺失即报错；sha256 覆盖**压缩包**而非其中的库 |
| zip 内容 | 有且仅有一个动态库，**必须在压缩包根目录**，名为 `<id><ext>` 或 `<id>-v<version><ext>` |
| 安装落点 | `plugins/<goos>/<goarch>/<id>-v<version><ext>` |

**前导 `v` 必须剥掉，这里有两次独立的拒绝。** 商店侧按裸版本拼资产名；宿主侧 `pluginhost.validPluginVersion` 明确拒绝以 `v` 开头的版本。因此 Makefile 用 `override`（而非普通赋值）做规范化——命令行传入的 `VERSION` 会覆盖 makefile 里的赋值，普通写法会让 `make VERSION=v0.1.0` 带着前缀流到注册元数据里。

**已实测的完整闭环**：用 `direct` 类型挂一个本地 registry，真实 CPA 实例返回 `status: installed`、`registered: true`、`version: 0.1.0`，落盘文件与源库逐字节一致，日志确认 `plugin registered ... version=0.1.0`。`github-release` 的资产解析未走真实 release 验证，但它与已实测的 `direct` 共用同一份 `InstallArchive`，且资产名由同一格式串生成（`cmd/release-archive` 有测试断言该名字）。

**两个容易踩的地方**：`install.type: direct` 的 URL 不允许带 query、fragment 或内嵌凭据；registry 用 `http://` 时需要一条匹配的 `allow-insecure` 授权规则（`plugins.store-auth`），发布到 GitHub 走 https 则不需要。

**Windows 构建需要 `-fuse-ld=lld`。** Go 的 c-shared 会把生成的 `.def` 交给外部链接器，而 Windows runner 自带的 binutils ld 2.46 在**产物名内嵌版本号**时解析不了它：

```
ld.exe: export_file.def:1: syntax error
ld.exe: export_file.def: file format not recognized; treating as linker script
```

在 Windows runner 上逐项隔离后确认，触发条件是名字里的点号而非长度：`probe.dll` 与 `codex-turn-state-manager.dll` 能链接，`codex-turn-state-manager-v0.1.0.dll` 与 `ctsm-v0.1.0.dll` 失败，而一个很长的、不含内嵌点号的名字可以。lld 读同一个文件没有问题，同一条命令加上 `-fuse-ld=lld` 即成功。该开关按宿主 GOOS 条件化在 Makefile 里，Windows 上本地 `make release-archive` 同样受益。binutils 修好后即可移除。



### 10.17 会话混淆有两个版本，静态资源必须带内容哈希

**`cli-proxy-auth` 的混淆格式有两个版本在同时流通。**

| 版本 | 密钥派生 | 谁在写 |
|---|---|---|
| `enc::v1::` | `<salt>\|<host>\|<userAgent>` | CPA 自带管理界面 |
| `enc::v2::` | `<salt>\|v2\|<host>` | CPA-Manager-Plus（它自己迁移过去的） |

v2 的存在理由正是 v1 的缺陷：把会话绑到 UA 上，浏览器一升级就解不开。面板只认 v1 时，读到 v2 会 `JSON.parse` 失败并报「格式无法识别」，而操作者明明已经登录过。两个版本都要按前缀分流解码——不能用「挨个试」的办法，XOR 用错密钥不会抛错，只会解出乱码，试错等于把乱码当数据。

**静态资源的路由名必须带内容哈希。** 实测一个真实部署：CDN 按扩展名分类，`.html` 原样透传，`.js` / `.css` 则被套上它自己的四小时 TTL，**覆盖插件设置的 `Cache-Control: no-cache`**。浏览器刷新过不去边缘缓存（强制刷新只能绕过浏览器自己的），于是更新后数小时内加载的仍是上一个版本的面板，而它调用的是已经不存在的管理路由。

解决办法不是查询串（`app.js?v=1`）——只按路径做键的缓存可以无视它——而是把内容哈希写进文件名：`/app.<hash>.js`、`/style.<hash>.css`。内容变则路由变，任何缓存都无法把两个版本混为一谈。`index.html` 是唯一不哈希的：它要留给宿主菜单一个稳定地址，而且它正是 CDN 不碰的那个文件，因此由它记录当前该加载哪一份资源最合适。

**引用必须是相对路径。** 面板挂在 `/v0/resource/plugins/<id>/` 下，`/app.<hash>.js` 这样的绝对路径会解析到站点根目录而 404。

### 10.18 代理冷却按「账号 × 代理」记账，不按代理

**同一个代理对不同账号的表现不同。** 上游按账号决定是否发放 turn state，所以一个代理可能对 A 账号返回目标长度、对 B 账号返回非目标长度。按节点冷却的后果是 A 的失败把 B 正在用的节点也拿走了——这是实测发现的，不是推演。

因此可用性记在 `(auth_index, proxy_id)` 上（迁移 v4 新增 `proxy_cooldown` 表）：

- 挑选节点时按账号过滤，被该账号冷却的节点对它不可选，对其他账号照常可选
- 一轮探测只在该账号**所有**节点都冷却时结束（`PROBE_NO_PROXY_AVAILABLE`）
- 阶梯与「到顶归零」都按这一组合独立计算
- 面板的代理列表不再有单一健康值，改为显示「N 个账号冷却中」；「详情」弹出该代理在每个账号上的状态，可逐条重置；另有全部重置

`proxy_node.consecutive_failures` 与 `proxy_node.cooldown_until` 保留但不再读取——迁移不重写，删列要走建新表/拷贝/删旧/改名的流程，而它们承载的数据已经无意义。

**代价要知道**：同一个代理在 N 个账号上失败就会产生 N 条记录，节点被完全闲置需要所有账号都把它冷却掉。这是刻意的——正是「对谁不可用」这件事本身需要被区分。

### 10.19 时间窗口闸门必须可见

「为什么凌晨还有探测记录」这个问题，答案有三种且**在面板上长得完全一样**：窗口被停用了、窗口的时间填错了、或者根本没有窗口。三者的语义都是「全天可探测」——`ShouldProbeNow` 只在存在*启用中*的窗口时才受限。

因此 `/status` 增加 `window` 字段，给出调度器的实时判定（`allowsProbe`）与当前启用中的窗口列表，面板配置行直接显示「窗口 08:00–02:00（当前禁止探测）」。操作者不该为了知道窗口是否生效去翻代码。

**手动探测刻意不受窗口限制。** 它是「现在探一次」的明确指令，而一个被关掉定时探测的 pair 恰恰是最需要手动验证的。按钮的 tooltip 写明了这一点，避免被误认为窗口失效。

**窗口按宿主进程的本地时区判定**（`at.Format("15:04")`），而面板时间戳按浏览器时区渲染、`/status` 的 `now` 报 UTC——三者可以互不相同。实测过一台 `TZ=Pacific/Honolulu` 而浏览器在 UTC+8 的实例：差 18 小时，`08:00–02:00` 的窗口在浏览器显示早上 7 点时服务端看到的是下午 1 点，探测照常。容器默认 UTC 时，操作者按本地时间配的 `08:00–02:00` 会整体偏移，表现为「深夜还在探测，而且很密集」。因此 `window` 字段同时给出 `serverClock`（**在服务端格式化好的墙钟时间**）、`serverTime`、`zone` 与 `offsetMinutes`，面板原样显示并在与浏览器不一致时直接报出差多少小时。

**`serverClock` 必须是服务端预格式化的字符串。** 用它走一遍 `new Date()` 会把它渲染成浏览器时区，而旁边的时区名仍然是服务端的——那等于同时说了两件矛盾的事，比不说更糟。这是本项目的第二次同类问题：闸门本身是对的，缺的是「它按哪个钟判定」这个信息。

### 10.20 State 形状按套餐区分，长度不是唯一值

**目标长度不是全局唯一值，它由账号套餐决定。** turn-state 是一个带结构的信封，不是随机串：

```
raw[0] == 0x80                          版本字节
raw[1:9]                                签发时间（大端 uint64）
Blocks = (len(raw) - 57) / 16           密文块数，须整除
```

**个人版 10 块 → 292 字符；Team / Business 版 12 块 → 332 字符**（实测值，非公开规格）。套餐归类与参考实现一致：

| `chatgpt_plan_type` | 规则 | 长度 |
|---|---|---|
| `team` / `business` | 团队 | 332 |
| `free` / `plus` / `pro` | 个人 | 292 |
| 其他 / 缺失 | 个人 | 292（或配置的兜底长度） |

**注意 Pro 属个人版，不是团队版。** 只有 Team 与 Business 走 12 块。所以 Team 账号正确的值，正是 Plus 账号的「错误长度」——用单一 `target_state_length` 无法同时描述两者。

判定因此从「长度相等」改为「形状相符」：读 token 自身的块数，与账号套餐推导出的期望块数比较。套餐来源优先取**当前响应的** `X-Codex-Plan-Type`（与值同一次响应到达，最新），其次取已记录的套餐，最后才回落到 `target_state_length`——**配置项只在套餐未知时生效**，这是它现在的确切含义。

信封读不出时不报错，仍按长度比较：上游改了信封格式的话，行为退回到改动之前，而不是一个值都绑不上。

**顺带修掉的一处**：标记「非目标」原来用 `len(value) != target_state_length`，Team 账号会被永久判为非目标而永远绑不上。

面板在每个账号上显示推导出的期望长度，操作者读探测记录时能看出用的是哪条规则。

**有效期从签发时刻起算，不从绑定时刻。** 信封里的 `issued` 就是为此存在的：

- `Policy.Expiry(issued, boundAt)` 以 `issued` 为锚（未知时才退回 `boundAt`；`issued` 晚于当前时间说明时钟有问题，不采信，否则等于凭空延长寿命）
- 到手时**已经超出 TTL** 的值不绑定。为此新增 `SUCCESS_STALE` 结果：形状对、但太旧。它**不冷却代理**——节点答对了，只是上游给的是一份旧值；重试节奏与非目标相同（2–5 分钟）
- `Bind` 自身也拒绝已过期的值（`ErrStateExpired`），作为调用方之外的兜底：一个生来就死的绑定不该顶掉还活着的那个
- 面板把 `SUCCESS_STALE` 显示为中性标记，并在计数行给出「过期值 N」

实测过：同一个值在 40/60 分钟时仍是 `FRESH`，55/60 时进入 `REFRESH_DUE`——这正是「知道它多老」才可能算准的东西。

### 10.21 连续非目标要退避，否则代价全落在代理上

一个永远拿不到目标长度的 pair（例如只返回 312 的模型），原来每 2–5 分钟重试一次、**永不停止**，而每一轮都会走一遍代理池。学习到的信息每轮都相同，付出的却是代理的信誉——这正是「代理反复被打」的来源。

现在间隔随连击增长：

| 连续非目标 | 下次探测 |
|---|---|
| 1–3 | 2–5 分钟（基数，带抖动） |
| 4 | ×2 |
| 5 | ×4 |
| … | 每轮翻倍 |
| 到上限 | `non_target_backoff_cap_min`，默认 30 分钟 |

前三次保持基数是有意的：连续两三次形状不对可能只是上游还没稳定，值得及时再试；超过之后就不是偶发了。**任何其他结果都会归零**，所以模型一旦开始给出正确形状，立刻回到基数节奏。

上限是「请求速率的下限」，不是「放弃期限」：到顶之后仍然探测，只是很久一次——上游随时可能改变对某个模型的行为。

同一套逻辑也覆盖 `SUCCESS_STALE`（值太旧）：它和非目标一样表示「等会儿再来」，也一样不该归咎于节点。

### 10.22 面板上的「未保存草稿」必须能活过一次刷新

代理池是同一份列表存在两个地方（本地编辑态与服务端），而**服务端的副本在每次往返时都胜出**。后果是：新添加但尚未填写地址的行，在每 15 秒的刷新落地时被整体覆盖抹掉——连同已经输入的内容。表现为「输入框消失、输入后没记录」，而输入框正在被编辑时消失，是因为重建整个表格会换掉光标所在的那个元素。

两处修正：

- **`mergeProxies(server)`**：服务端未确认的行（本地标记 `draft`）予以保留。匹配用的是**地址而不是 id**——id 由地址推导（取其 host），一旦填上地址就变了，按 id 匹配会把刚保存成功的行当成未知而保留两份。按地址匹配同时意味着：在别处被删掉的节点不会被本地旧副本复活。
- **渲染时若表格内有输入框持有焦点则跳过重建**，把「正在进行的编辑」置于后台刷新之上；操作者离开该字段后的下一次渲染会带上所有变化。

**顺带删掉一处死代码**：`on("save-proxies", ...)` 绑定的是一个早已从 HTML 移除的按钮，它重复了整套保存逻辑并且保留着旧缺陷。静态检查器之所以能发现它，是因为「服务端列表被整体采纳」这件事必须只有一条路径——两条就是两个真理。

**检查器本身也修了一处**：`TestPanelCallsOnlyDefinedFunctions` 扫的是原始文本，注释里的 `address (its host)` 被判成对未定义函数的调用。现在只剥**整行注释**——朴素地剥 `//` 之后的内容会在 `http://...` 处截断代码行，那比误报更糟。

### 10.23 构建要求

CPA v7.3.7 的 `go.mod` 要求 **Go 1.26**。本插件因此将 `go 1.26.0` 写入自己的 `go.mod`，并直接依赖 `github.com/router-for-me/CLIProxyAPI/v7`——SDK 的 `sdk/pluginabi` 与 `sdk/pluginapi` 只依赖标准库，但通过模块依赖可以避免手抄类型定义带来的漂移。
